Message bodies

The header says who signed. The body says what they said.

A list of fields

Each message type that has a schema lists its fields in order. P2P_PING is one field, nonce. The header hash is double-SHA256 of the body bytes. Peers drop a frame whose hash does not match.

The first frame has no parent

The header's parent is the id of the previous message, or 32 zero bytes when this frame starts a chain. The sign-and-verify script checks that a new message is still at genesis. Later durable frames set the parent before they sign.

Zeros until there is a secret

The preimage slot is a payment secret. Ordinary public messages leave it as 32 zero bytes. A circuit or an HTLC puts an explicit 32-byte secret there, and the payment hash is SHA256 of that secret. The slot is not a second copy of the body hash.

Some bodies are just text

P2P_CHAT_MESSAGE carries UTF-8 with no field schema. That is the shoutbox frame from the first walkthrough.

JSON lives at HTTP

Peers speak fields. Browsers and HTTP speak JSON. @fabric/http is that door: examples/message-bridge.js turns a ping into fields and back, and it stores one sidechain patch as canonical fields while still offering the RFC6902 list to the page. It does not start a server.
